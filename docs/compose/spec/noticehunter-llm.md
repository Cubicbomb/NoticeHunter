## Report

**What was built** — 把原纯正则抽取层改造成 **LLM 主抽取 + 规则兜底**：新增 OpenAI 兼容调用层（`POST {base}/chat/completions`，15 秒/次超时，HTTP 非 2xx、响应非 JSON、内容不可解析、返回空数组、结构缺字段五类失败各自给出具体中文原因）；三字段设置面板（Base URL / Key / Model）**只存内存**，不写 `localStorage`、不进 URL、不进 DOM 属性、不出现在导出文本中，刷新即清空；候选段落由规则前置筛选，仅把含日期或模糊时间词的段落送模型，超过 60 段则**分批顺序发送**（不是截断）；模型返回逐字段校验——`due` 格式非法由规则层从 `dueRaw` 修正，`sourceIndex` 越界整条丢弃并提示剔除条数，置信度非法回落 `low` 并记原因；页头常驻模式徽章、卡片与清单标注 `AI` / `规则式` 来源、提供手动重试。**规则层没有被删除**，降级为三用：候选筛选、字段校验与修正、无 Key / 断网时的离线兜底——因此未配置时零网络请求、断网可完整演示这条硬约束依然成立，原有四道差异化设计（人工确认、出处高亮、跨文件去重撞期、只输出动作）一条未动。

**Verification** — `node --check` 对提取出的内联脚本通过（约 41.5KB）。两套浏览器验收：`node prototype/verify.cjs`（仅静态服务器、**不配 Key**）**30 PASS / 0 FAIL**，含原 `noticehunter-mvp` 全部 29 项 + 新增「零外部网络请求」断言；`node prototype/verify-llm.cjs`（静态服务器 + `prototype/test/fake-llm-server.js` 本地 OpenAI 兼容桩）**44 PASS / 0 FAIL**，覆盖 T1–T7，其中故障回退后的「确认 → 清单 → 导出」在 `http-500` / `bad-json` / `timeout` 三种模式下各走一遍，65 段候选文件断言分成 **2 次**请求（可证伪分批回归）。三轮独立评审：首轮 2 critical → 全部修复；复审 2 critical（均为验收覆盖不足）→ 全部修复；第三轮**无 critical**，spec compliance / correctness / codebase consistency 三项结论均为 PASS。

**Journey log**
1. **正则是 MVP 约束，不是产品智能** — D-005 让 MVP 只用正则，换来零依赖、断网、可测；但实测暴露「谁」被判成签字人、动作剥出残渣、「考试前一天」类表述无解。教训：**换抽取引擎不动摇产品差异化**，因为四道设计都在抽取层之上。
2. **规则层降级而不是删除** — 把它拆成候选筛选 / 字段校验 / 离线兜底三用，既保住 `AGENTS.md` 第 7 节「无 Key 必须可演示」的硬要求，又让规则做它比模型更擅长的事（日期归一、确定性）。
3. **静默截断是最隐蔽的 bug** — `selectCandidateParagraphs` 用 `slice(0, 60)` 而非分批，61 段之后既不发也不走规则，**悄悄丢召回**。修复后用一个 65 行文件断言「恰好 2 次请求」，让截断回归无法蒙混过关。
4. **验收措辞本身可能不可满足** — T4 原话「该文件仍以规则模式产出结果」被评审判定为不可满足（无日期文件在两种模式下都产不出条目），**改 spec 而不是硬凑代码**。教训：写验收时先问「这个断言能否被证伪」。
5. **测试读错对象比产品 bug 更难查** — 曾用 `#reviewList` 的 `innerText` 断言动作字段，而动作在 `<input>` 的 `value` 里，`innerText` 只返回 label 文本，一度误判为产品故障；同类问题还有 `locator('#reviewList').count()` 恒为 1 的容器级空断言。**断言必须落在真正承载数据的属性上。**

**已知未修 minor（第三轮评审记录，均为测试质量或文案一致性，不影响验收）**
- `prototype/verify-llm.cjs`：`bad-json` 那次导出断言可被前一次 `http-500` 已确认条目预先满足，该次「确认动作」未被独立验证。
- `prototype/verify-llm.cjs`：T4 阶段二的 `#clear` 使「其余文件不受影响」在重试场景下只剩阶段一（未重试）覆盖。
- `prototype/index.html`：三处「抽取进行中」提示文案不统一（`AI 抽取进行中` / `抽取进行中`）。
- `prototype/verify-llm.cjs`：T1 静态断言里 `indexOf('test/')` 子串匹配偏脆（会匹配 `latest/`）。

## [S1] Problem

当前抽取层是纯正则（D-005），而通知本质是自然语言。实际运行已经暴露三类不可修的缺陷：

1. **角色判错**——「请于本周内提交书面申请，经**任课教师**签字后交至教务办」，`owner` 被抽成**签字的人**而非**办事的人**。正则匹配的是句中出现的组织角色，没有「施动者」概念。
2. **动作字段残渣**——把 owner 从句中剥掉后剩下「经 签字后」，说明基于子串删除的还原方式在语义上不成立。
3. **转述无解**——「考试前一天」「详见附件」「以系统关闭时间为准」这类真实通知高频写法，正则没有对应模式，只能一律标低置信度推给人工。

同时存在一个参赛层面的隐患：决赛评分「技术应用 25%」考的是**「AIGC 工具的综合与深入运用能力，技术方案或工作流设计的合理性」**，而产品运行时完全不调用任何模型。

**约束不变的部分**：`AGENTS.md` 第 7 节硬要求「没有 key 时必须能用内置模拟数据完整演示」；四道差异化设计（只输出动作、出处高亮、人工确认、跨文件去重撞期）全部位于抽取层之上，与抽取引擎无关。

## [S2] Design

### S2.1 架构：LLM 主抽取，规则层降级为筛选与兜底

- **解析**（`.txt` / `.docx` → 段落数组）仍由 JS 负责，**不进 LLM**——它确定、免费、已有 29 项验收覆盖。
- **抽取**分两条路，产出**同一数据模型**（沿用既有 `TodoItem`），下游（人工确认 / 清单 / 撞期 / 导出）零改动：
  - **AI 模式**：已配置 `base + key + model` → 调用 OpenAI 兼容 `POST {base}/chat/completions`
  - **规则模式**：未配置 / 网络失败 / 超时 / 返回不可解析 / 字段非法 → 回退既有正则抽取
- 规则层的三个新职责（**不是被删除，是被降级**）：
  1. **候选段落筛选**——只把含日期或模糊时间词的段落送进 LLM（见 S2.5）
  2. **字段校验与修正**——校验 LLM 返回的 `due` 格式与 `sourceIndex` 范围（见 S2.4）
  3. **离线兜底**——无 Key / 断网时保证主流程完整可用（见 S2.9）

### S2.2 配置与密钥管理

- 设置面板三个字段：**API Base URL**、**API Key**、**Model**。
- **只存内存**（模块级变量）：
  - 不写 `localStorage` / `sessionStorage`
  - 不进 URL、不进 `data-*` 属性、不写入日志
  - 不出现在导出文本中
  - 页面关闭即清空
- Key 输入框 `type="password"`。
- **不预设任何平台地址或默认值**——避免在仓库里硬编码第三方端点。
- 三项齐备才算「已配置」；缺任一项即视为未配置，走规则模式。

### S2.3 调用契约

```
POST {base}/chat/completions
Authorization: Bearer <key>
Content-Type: application/json

{
  "model": "<配置项>",
  "temperature": 0,
  "messages": [
    { "role": "system", "content": "<抽取任务说明 + JSON schema 约束>" },
    { "role": "user",   "content": "<文件名 + 段落编号与正文>" }
  ]
}
```

- 响应取 `choices[0].message.content`，解析为 JSON 数组。
- **超时**：`AbortController`，超时常量 `LLM_TIMEOUT_MS = 15000`。
- **不自动重试**（避免不可预测的重复计费与不可预测行为）；失败即回退，并提供手动「重新尝试 AI 抽取」按钮。
- **以下任一情况视为失败并回退**：非 2xx 状态、超时、`content` 非 JSON、解析结果不是数组、数组为空。
- 失败时 toast 必须给出**具体原因**（HTTP 状态 / 超时 / JSON 解析失败），不得只说「失败」。

### S2.4 LLM 输出 schema 与规则校验

LLM 必须返回 JSON 数组，元素结构：

```json
{
  "action": "交什么 / 做什么",
  "owner": "谁，无法识别为 null",
  "where": "交到哪，无法识别为 null",
  "dueRaw": "原文中的时间表述，原样保留",
  "due": "YYYY-MM-DD 或 YYYY-MM-DD HH:mm；模糊时间为 null",
  "sourceIndex": 14,
  "confidence": "high | low",
  "reasons": ["低置信度原因，可为空数组"]
}
```

**规则层校验（不信任 LLM）：**

| 字段 | 校验 | 不通过时 |
| --- | --- | --- |
| `due` | 必须匹配 `^\d{4}-\d{2}-\d{2}( \d{2}:\d{2})?$` | 用规则层从 `dueRaw` 重算；仍失败 → `due = null` 且置 `low` |
| `sourceIndex` | 必须为整数且落在该文件段落区间内 | **丢弃该条**并计数（防止幻觉定位导致出处跳转错位） |
| `action` | 非空字符串 | 丢弃该条 |
| `confidence` / `reasons` | 白名单校验 | 非法值回落为 `low` 并写入原因 |

校验剔除条数若 > 0，需在界面上提示「AI 返回的 N 条已剔除」。

### S2.5 请求粒度与候选筛选

- **按文件为单位**：一个文件的全部候选段落合并进一次请求，不逐段调用。
- **先筛后送**：仅当段落命中现有规则的日期或模糊时间模式时才进入请求体。
  - 无候选段落 → **不发任何请求**。
  - 这同时是成本控制与召回保障：规则保证不漏，LLM 负责理解。
- 单次请求段落数上限常量 `LLM_MAX_PARAS = 60`，超过则分批顺序发送。
- **顺序发送**，同一时刻只有一个文件的请求在途（不做并发）。

### S2.6 并发、失败与重试

- 请求在途时，界面显示进行中状态并禁用重复触发。
- 失败 → toast 说明原因 → 该文件**整体回退规则式**（不出现半截结果）。
- 手动「重新尝试 AI 抽取」仅对当前会话生效，可反复触发。
- 多文件场景：逐文件独立成功或回退，**单个文件失败不影响已载入的其他文件**。

### S2.7 模式指示与可解释性

- 页头**常驻徽章**：`AI 抽取`（蓝） / `规则式抽取（兜底）`（灰）。未配置 key 时始终显示后者。
- 每张待确认卡片与每条清单项新增来源标注：`AI` / `规则式`。
- 数据模型新增字段 `extractor: 'ai' | 'rule'`，导出文本中**不输出**该字段（避免污染交付物），只在界面显示。

### S2.8 与既有四道设计的关系

- 只输出动作、出处高亮、**人工确认**、跨文件去重撞期——**全部保持不变**。
- **AI 给出 `high` 置信度仍必须人工点确认**，不让模型替人拍板（`S2.6` of `noticehunter-mvp.md` 原样继承）。
- 出处跳转依赖 `sourceIndex`，因此该字段必须由 JS 校验（S2.4），不信任模型自报。

### S2.9 离线与无 Key 演示（硬约束，`AGENTS.md` 第 7 节）

- 未配置 `base/key/model` → **不发出任何网络请求**，直接走规则模式。
- 断网 / 请求失败 → 规则模式兜底，**主流程不中断**。
- 内置样例在规则模式下必须仍能完整走通 `noticehunter-mvp.md` 的全部 29 项验收。

### S2.10 测试策略

LLM 输出非确定性，不能靠真模型做断言。方案：

- 新增 **本地 stub 服务** `prototype/test/fake-llm-server.js`：仅用 Node 标准库 `http` 实现 OpenAI 兼容 `POST /chat/completions`，返回固定 JSON。
- 测试通过设置面板把 Base URL 指向 `http://127.0.0.1:<port>`，**走真实 `fetch` 路径**（不 mock 页面内部函数）。
- stub 支持切换故障模式：`ok` / `http-500` / `bad-json` / `timeout`，用于覆盖 S2.3 的失败分支。
- stub **仅供测试**，产品零依赖的性质不变；不引入任何 npm 包。

### S2.11 硬安全上限（防失控计费）

> **修订（2026-10-14 交付后追加）**：S2.1–S2.10 交付后的既有约束是**限流性质**（单次超时、单请求段落上限、单飞、不自动重试），缺**预算性质**的硬上限。真实的失控路径不是死循环（已被单飞与超时堵住），而是**一个超大输入或反复重试，静默发出几十上百次请求而用户毫无感知**。本节补上封顶。

#### S2.11.1 常量

| 常量 | 值 | 作用 |
| --- | --- | --- |
| `LLM_MAX_TOKENS` | `2048` | 每次请求的 `max_tokens`，封死输出膨胀 |
| `LLM_MAX_PARA_CHARS` | `2000` | 单段落送模型的字符上限 |
| `LLM_SESSION_REQUEST_CAP` | `60` | 单个会话累计请求上限 |
| `LLM_MIN_INTERVAL_MS` | `800` | 两次 HTTP 请求之间的最小间隔 |
| `LLM_CONFIRM_THRESHOLD` | `200` | 候选段落数超过此值时先确认 |

会话状态新增 `state.llmRequests`（累计已发出的 HTTP 请求数，含失败的）。

#### S2.11.2 行为契约

1. **输出上限**：`callLLM` 的请求体必须包含 `max_tokens: LLM_MAX_TOKENS`。
2. **单段落截断**：送模型前，候选段落文本超过 `LLM_MAX_PARA_CHARS` 时截断到该长度。**只截断送给模型的副本**；`sourceText` 与原文区仍保留完整原文。对应待确认卡片增加一条 reason：`原文段落超长（N 字），已截断送模型`。
3. **会话请求预算**：
   - `callLLM` 在发出请求前 `state.llmRequests++`（失败的请求也计数——它们已经产生了计费风险）。
   - `state.llmRequests >= LLM_SESSION_REQUEST_CAP` 时**不再发起任何 AI 请求**，该文件直接走规则式。
   - 触顶时：toast 说明「本会话 AI 请求已达上限 60 次，已改用规则式抽取」；页头徽章显示「AI 抽取 · 预算已用尽」；**重试按钮禁用**。
   - 预算在**清空会话**时归零（与 `state.sessionId++` 同一处）。
4. **最小请求间隔**：连续两次 HTTP 请求之间至少间隔 `LLM_MIN_INTERVAL_MS`。**分批循环与跨文件循环都必须遵守**（间隔在 `callLLM` 内部实现，调用方无需关心）。用 `await sleep()`，不阻塞 UI。
5. **大操作确认**：某文件候选段落数 > `LLM_CONFIRM_THRESHOLD` 时，先弹出 `window.confirm`：「该文件有 N 段候选，将分约 M 次请求调用模型，是否继续？」。**取消 → 该文件直接走规则式，不发任何请求**。用原生 `confirm()` 而非自定义对话框——静态单文件页最小实现，且可被自动化测试驱动。
6. **消耗可见性**：设置面板内显示 `本会话已发 N / 60 次请求`，每次请求后刷新。让用户始终能看到消耗，而不是等触顶才知道。

#### S2.11.3 不变的部分

- 不自动重试（S2.6）、单飞（S2.6）、无 Key 与失败回退（S2.9）、四道差异化设计（S2.8）**全部不变**。
- 本节新增的是**在已有约束之上再加一层封顶**，不是替换。

## [S3] Out of Scope

明确不做，避免范围蔓延（`AGENTS.md` 第 4 节：材料 > 功能）：

- **deadline 汇总视图**——本轮不做，已记入 `HANDOFF.md` 待办（下一迭代）。
- **交互布局优化**（待确认计数与筛选、丢弃撤销、分屏、原文展开）——同上，已记入待办。
- **改投赛题二 / 做成 skill**——维持 **D-001**（赛题一），不做 skill。
- 预设第三方平台地址或默认 key。
- 配置持久化到 `localStorage`。
- 流式输出、多轮对话、对话上下文记忆。
- 自动重试、请求队列、并发调用。
- **把 `LLM_SESSION_REQUEST_CAP` 做成设置面板可调项** —— 会话预算固定为常量。理由：可测性可以靠「连续重试到触顶」解决（stub 响应很快，但受 800ms 节流影响，触顶测试约需 50 秒——这是该安全特性的固有代价，不是缺陷），不值得为测试方便而给用户一个能自己调高的危险开关。
- **token 成本估算与费用显示** —— 无法在客户端可靠折算，不做。
- PDF 解析、图片 OCR。
- 日历导出、多人分工、提醒推送。
