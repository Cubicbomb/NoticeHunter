# P-001 · 单文件 MVP 原型的生成与两轮迭代

- **日期**：2026-10-13 ~ 2026-10-14
- **工具**：MiMo Desktop（会话内多智能体；实现由主智能体完成，评审由独立 `general` 子智能体完成）
- **模型环节**：需求澄清 → 规格撰写 → 前端代码生成 → 独立评审 → 缺陷修复
- **输入**：竞赛通知 docx 原文、`AGENTS.md` / `HANDOFF.md`、用户在 Grill 环节的三次选择、`docs/compose/spec/noticehunter-mvp.md`
- **上游**：无（首条）
- **状态**：采用

## Prompt 原文

用户原始指令（逐字，未润色）：

```
/compose-next 所以该怎么构建这个项目，如何实现？
```

随后经 `compose-next` Grill 环节，由用户三次点选确定的约束（逐字）：

```
选题：《通知猎人》· 赛题一（推荐）
工作区：开 worktree + 分支（推荐）
抽取方案：MVP 只做规则式抽取（推荐）
Spec 批准：批准，开始实现（推荐）
```

实际驱动代码生成的规格文档为 `docs/compose/spec/noticehunter-mvp.md`，其中
`[S2] Design` 的 12 个小节与 `Tasks` 的 T1–T9 验收标准构成完整指令集。规格的核心硬约束：

```
- 单文件 prototype/index.html，HTML+CSS+JS 全内联
- 零构建、零 npm 依赖、零外部网络请求
- 可从 file:// 直接双击打开，也可用本地静态服务器访问；两种方式表现一致
- 内置样例文本以 JS 字符串常量内联，不得用 fetch() 读取
- .docx 解析：手写 ZIP 中央目录 + DecompressionStream('deflate-raw')，禁止引入任何库
- 规则式抽取：所有规则均为确定性正则/字符串匹配，不调用任何模型
- 低置信度条目必须人工确认后才进入行动清单，不让程序替人拍板
- 所有错误路径必须可恢复，任何情况下页面不得白屏或抛出未捕获异常
```

## AI 输出（关键片段）

单文件约 900 行：内联样例 → 文件/拖放输入 → 手写 ZIP 解析 → 正则抽取（日期 / 模糊时间 /
截止标记 / 交件地点 / 责任人）→ 待确认面板 → 行动清单 → 撞期与去重 → 出处跳转 → 文本导出。
另产出 `prototype/verify.cjs` 浏览器验收脚本（29 项断言）。

## 观察

**成功**
- 规格先行（先写 S1–S3 与 T1–T9，再动手）让两轮评审都有可对照的验收标准，而不是凭感觉判断「做完了」。
- 零依赖约束下的 `.docx` 解析方案成立：手写 ZIP + 浏览器原生 `DecompressionStream` 即可，
  不需要任何库，`file://` 直开可用。

**问题（AI 生成代码里实际出现的缺陷，按发现顺序）**
1. `String.split(regex)` 带捕获组会把捕获组插回结果 —— 导致日期被拆成 `2026 12 25` 残留在动作字段里。
   自查阶段由输出文本异常暴露。
2. 星期括注正则只匹配单字 `（四）`，漏掉 `（周四）`，动作字段残留「（周四）」。
3. **独立评审首轮 3 项 critical**：
   - S2.5「截止标记」规则完全未实现；
   - S2.7 撞期提示文案与 spec 写死的句子不符，而测试只 grep 日期，把漂移掩盖了；
   - T7 导出测试是同义反复 —— 在 `page.evaluate` 里自己重写一遍导出逻辑再断言自己，恒为真。
4. 日期与时间之间夹「（周四）」时，新写的合并正则吃不掉时间和标记。
5. 评审 minor：`hasMarker` 的 40 字符窗口会把「考前」「提前」误判成截止标记。

**人工核查情况**
- 逐条检查了 AI 产出的中文文案与正则，发现并修正了上面 1、2、4 三条 AI 自查未暴露的问题。
- 评审指出的 3 项 critical 全部由人工确认复现方式后才动手改，没有「照单全收」：
  其中第 3 条的根因是**测试写法有问题而非产品有问题**，改的是测试而非产品逻辑。
- 样例数据逐字核对：`prototype/samples/` 三份均为虚构，不含任何真实姓名 / 学号 / 联系方式。
