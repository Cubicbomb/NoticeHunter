# P-002 · LLM 结构化抽取的 system prompt

- **日期**：2026-10-14
- **工具**：MiMo Desktop（主智能体实现，独立 `general` 子智能体三轮评审）
- **环境环节**：抽取阶段（载入通知 → 段落 → 结构化条目）。解析与校验在 JS 侧，本条只记模型提示词。
- **输入**：`prototype/samples/` 两份模拟通知、竞赛通知原文；`docs/compose/spec/noticehunter-llm.md` 的 S2.3 / S2.4
- **上游**：P-001（原型实现，当时为纯正则）
- **状态**：采用

## Prompt 原文

（与 `prototype/index.html` 中 `LLM_SYSTEM_PROMPT` 逐字一致，此处归档供评分附录引用）

```
你是校园通知结构化抽取器。输入是通知的段落列表，每行以「编号. 正文」给出。
请抽出其中可执行的待办事项，**只输出一个 JSON 数组，不要任何解释、不要 markdown 代码块**。
数组元素结构：
{"action":"交什么或做什么，不含时间与礼貌用语","owner":"动作的执行者，识别不到为 null",
"where":"交到或发送到的地点/渠道，识别不到为 null",
"dueRaw":"原文中的时间表述，原样保留","due":"归一化为 YYYY-MM-DD 或 YYYY-MM-DD HH:mm，时间模糊则为 null",
"sourceIndex":段落编号（整数，必须来自输入，禁止编造）,
"confidence":"high 或 low","reasons":["低置信度原因，可为空数组"]}
规则：due 为具体日历日期时 confidence 才能是 high；出现「本周内」「下周三之前」「考试结束后一周内」等模糊表述时 due 必须为 null 且 confidence 为 low。
注意区分动作的执行者与签字人/审核人：owner 应是办事的人。
```

调用参数：`temperature: 0`；按文件批量送候选段落，单请求上限 60 段，超出分批顺序发送。

## AI 输出

由 stub 与真实模型分别产出，形态一致：JSON 数组，元素如上 schema。真实模型可能把 JSON 包进 ```` ```json ```` 围栏，故客户端有 `stripFences()` 剥离。

## 观察

**成功**
- 最后一句「注意区分动作的执行者与签字人/审核人，owner 应是办事的人」直接对应正则层修不掉的缺陷：「请于本周内提交书面申请，经**任课教师**签字后交至教务办」，正则把 owner 判成签字人，这条提示词是为此加的。
- 把「只输出 JSON 数组，不要解释、不要 markdown 代码块」写死后，仍遇到模型包围栏的情况，故保留了 `stripFences` 兜底——**提示词约束不能替代代码容错**。

**问题（客户端必须兜住的，已全部实现校验）**
- `due` 可能返回非归一化格式 → 规则层从 `dueRaw` 重算，失败则置 `null` 并记原因。
- `sourceIndex` 可能被编造 → 越界整条丢弃并提示剔除条数，否则出处跳转会指向错误段落。
- `confidence` 可能不在白名单 → 回落 `low` 并记原因。
- 可能返回空数组 → 视为失败并回退规则式。

**人工核查情况**
- system prompt 由人工逐句核对：字段名与 `TodoItem` 数据模型一一对应；「不要代码块」一条是针对实际观测到的模型行为加的，不是想当然。
- 三轮独立评审中，评审确认「不信任模型返回、逐字段校验」这一设计成立，并指出校验分支此前缺少测试（S2.4 非法置信度），已补测试用例。
- 未在本仓库写入任何第三方平台地址或默认模型名——避免硬编码端点，也避免把某一家供应商写进作品。
